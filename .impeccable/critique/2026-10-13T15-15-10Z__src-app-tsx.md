## Design specificity และสิ่งที่ทำได้ดี

หน้าจอสีขาว ปุ่มหลักสีน้ำเงิน และเส้นแบ่งมีความสม่ำเสมอ จุดเฉพาะของผลิตภัณฑ์อยู่ที่การแยกสี/ไซซ์และหน่วยขาย การแสดงยอดก่อน–หลัง และบิลกระดาษที่คุ้นเคย ส่วนกรอบเมนูยังเป็นหน้าจอจัดการทั่วไปซึ่งเหมาะกับงานนี้ ไม่จำเป็นต้องเพิ่มของตกแต่ง

- รับเข้า จ่ายออก และตรวจนับ อธิบายผลต่อยอดก่อนบันทึกได้ชัด
- เลือกสินค้า → สรุป → ยืนยันออกบิล มีจุดตัดสต๊อกชัด และซ่อนข้อมูลบิล/ราคาพิเศษไว้จนจำเป็น
- หน้าบิลมีรายการที่อ่านง่ายควบคู่กับหน้ากระดาษ และแยกหน้าที่ของหน้าจอกับเอกสารได้ดี

## ผลรายหน้า

| หน้า | ความเห็น |
|---|---|
| Inventory | แยกประเภทถูกหน้าที่ แต่รายการบนมือถือสูงและมี label ซ้ำ; หน้าเริ่มว่างควรให้เพิ่มสินค้าแทนล้างตัวกรอง |
| เพิ่ม/แก้สินค้า และเพิ่มประเภท | ฟอร์มหน้าเดียวเข้าใจง่าย; error ต้องอยู่ใกล้ช่องผิด; หัวข้อเพิ่มสินค้าซ้ำ; เปิดใช้งานสินค้าไม่ตรง flow ล่าสุด |
| จัดการสต๊อก | รับเข้า/จ่ายออก/ตรวจนับแยกชัด; ประวัติรวม 30 รายการยังตอบคำถามราย SKU ได้ยาก |
| รับเข้า/จ่ายออก/ตรวจนับ | ยอดเดิมและยอดใหม่ช่วยตรวจงาน; กรณีจ่ายเกินแจ้งจำนวนสูงสุดชัด |
| ทำบิล—เลือกสินค้า | ค้นหาและกดซ้ำเพิ่มจำนวนได้ตรงงาน; ตะกร้าควรมีทางกู้คืนเมื่อ refresh |
| สรุปรายการขาย | ยอดรวมและปุ่มยืนยันชัด; ข้อมูลเสริมพับไว้เหมาะสม |
| รายการขาย | ค้นหา/กรองสถานะได้; ควรแสดงชื่อลูกค้าเมื่อมีข้อมูล เพื่อช่วยแยกบิลที่ยอดใกล้กัน |
| เปิดบิล/ดูภาพบิล | ภาพกระดาษและสรุปอ่านง่ายแยกกันเหมาะสม; รักษา composition นี้ไว้ |
| แก้บิล/ยกเลิก/พิมพ์/ส่งออก | อ่าน source แล้ว แต่รอบนี้ยังไม่ได้เดินครบทุก interaction หรือทดสอบไฟล์ส่งออกใหม่ จึงไม่ให้คำรับรองว่าผ่านทั้งหมด |

## 5 เรื่องที่ควรแก้ตามลำดับ

1. **P1 — ตะกร้าหายเมื่อ refresh โดยไม่มีการเตือน**
   - เพิ่มสินค้าในตะกร้าแล้วรีโหลด พบกลับเป็น 0 รายการ เป็นพฤติกรรมที่เอกสารบันทึกไว้ แต่ยังเป็นความเสี่ยงต่อการขายที่ถูกขัดจังหวะ
   - แนะนำเก็บตะกร้าชั่วคราวใน session และเสนอให้ทำต่อ หรืออย่างน้อยเตือนก่อนออก โดยไม่เพิ่มขั้นตอนบันทึกร่างและไม่ตัดสต๊อก
   - Source: src/App.tsx:161,206; คำสั่งที่เหมาะ: impeccable harden
2. **P2 — กรอกสินค้าผิดแล้วมองไม่เห็น error**
   - ตรวจซ้ำได้ทั้ง 320 และ 390px: กดเพิ่มสินค้าขณะข้อมูลว่าง หน้าจอค้างที่ปุ่มล่าง แต่ข้อความผิดอยู่เหนือ viewport ไม่มี aria-invalid ที่ช่อง
   - แสดงข้อความข้างช่อง ระบุช่องบังคับ และเลื่อนพร้อม focus ไปช่องผิดแรก
   - Source: src/SimpleProductForm.tsx:32; คำสั่งที่เหมาะ: impeccable harden
3. **P2 — ประวัติสต๊อกยังหาสาเหตุรายสินค้าได้ยาก**
   - แสดงเพียง 30 รายการล่าสุดรวมทุกสินค้า อยู่ท้ายรายการบนมือถือ ไม่มีกรองรายสินค้า/วันที่หรือเปิดรายการเก่า
   - คง preview ล่าสุดไว้ แล้วเพิ่มทางดูประวัติของ SKU ที่เลือกและรายการก่อนหน้า เป็นข้อเสนอขยาย UX ที่ต้องตกลงขอบเขตก่อนทำ
   - Source: src/StockManagement.tsx:9; คำสั่งที่เหมาะ: impeccable shape
4. **P2 — ยังมีเปิดใช้งานสินค้า ทั้งที่ flow ล่าสุดใช้ลบสินค้า**
   - มี checkbox จริงในหน้าแก้ไข เมื่อปิด สินค้าอาจหายจากงานขาย/สต๊อกแต่ยังอยู่ใน Inventory ทำให้ต้องเข้าใจสถานะเพิ่มอีกชุด
   - ปรับให้ตรง flow ที่ตกลง และกำหนดวิธีรับมือรายการ inactive เดิมโดยรักษายอดและประวัติ
   - Source: src/SimpleProductForm.tsx:42; คำสั่งที่เหมาะ: impeccable clarify
5. **P2 — Inventory บนมือถือใช้พื้นที่มากก่อนเห็นสินค้าครบ**
   - ภาพ 390px เริ่มรายการแรกประมาณ 465px และเพียง 3 สินค้ายาวประมาณ 1500px ข้อมูลประเภท ราคา คงเหลือ และจัดการซ้ำเป็นหลายชั้น
   - จัดชื่อ/สี/ไซซ์ใกล้กัน วางราคาและคงเหลือในแถวเดียว ลด label ซ้ำและช่องว่าง โดยรักษาขนาดกดที่สะดวก
   - Source: src/InventoryAdmin.tsx:14, src/ebay.css:322; คำสั่งที่เหมาะ: impeccable adapt

## Cognitive load / personas / emotional journey

4 เมนูหลักและ 3 คำสั่งสต๊อกยังแบ่งงานได้ดี ไม่พบจุดตัดสินใจหลักที่มีตัวเลือกเกิน 4 อย่างจนเป็นปัญหา ช่องข้อมูลบิลเสริมหลายช่องยังยอมรับได้เพราะพับซ่อนได้ จุดที่เพิ่มภาระคือจำตะกร้าใหม่เมื่อหาย ค้นหา error นอกจอ และไล่ประวัติรวม จัดเป็น 3 ประเด็นระดับปานกลางใน checklist ของการประเมินนี้

- ผู้ใช้ครั้งแรก: ไม่รู้ช่องที่จำเป็นล่วงหน้า และหน้าเริ่มว่างให้ล้างตัวกรองที่ไม่มีประโยชน์
- ผู้ขายที่ถูกรบกวนระหว่างใช้มือถือ: รีโหลดแล้วต้องจำรายการใหม่ และเลื่อนหลายครั้งเพื่อเทียบ SKU
- ผู้ตรวจสต๊อกประจำ: ขาดทางเจาะประวัติของ SKU ที่กำลังมีปัญหา

ความมั่นใจเพิ่มขึ้นเมื่อเห็นยอดก่อน–หลังและข้อความออกบิลสำเร็จ แต่ลดลงเมื่อกดแล้วมองไม่เห็นเหตุผลที่บันทึกไม่ได้ หรือกลับมาแล้วตะกร้าหาย ทั้งหมดเป็นข้อสังเกตของ UI ไม่ใช่การเหมารวมผู้ใช้ตามอายุ
